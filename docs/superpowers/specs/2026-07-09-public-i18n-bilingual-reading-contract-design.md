# Public I18n And Bilingual Reading Contract Design

Date: 2026-07-09
Status: Proposed
Parent package: [2026-07-09-product-optimization-spec-review-package.md](./2026-07-09-product-optimization-spec-review-package.md)

## Summary

The product serves Chinese and English UI around dense AI technical articles. Language cannot be treated as a late copy pass. It affects navigation, metadata, article rendering labels, search recovery, Agent controls, owner routes, SEO, and mobile fit.

This spec makes bilingual behavior an implementation contract for public reading surfaces. It does not require translating article bodies.

## Goals

- Keep all public UI controls bilingual where the surrounding surface already uses i18n.
- Prevent hard-coded reader-facing English in Markdown rendering and discovery surfaces.
- Preserve route, query, and hash when language changes.
- Keep Chinese and English labels readable on mobile and narrow Agent panels.
- Keep SEO language metadata consistent with runtime language.

## Non-Goals

- No automatic translation of article content.
- No new i18n framework.
- No locale-specific routing such as `/zh` or `/en`.
- No machine translation pipeline.

## Runtime Contract

Language state should:

- Initialize from stored user preference when valid.
- Fall back to browser language when useful.
- Fall back to the project default when storage or browser language is unavailable.
- Update `document.documentElement.lang`.
- Preserve the current path, query string, and hash.
- Not require a full route reload.

## Copy Ownership

Reader-facing strings should live in the existing `client/src/i18n/*` modules unless the file already has a narrow documented exception.

Must be covered:

- Header navigation.
- Theme and language controls.
- Search states and recovery suggestions.
- Archive/taxonomy empty states.
- Article metadata labels.
- Markdown-generated UI labels such as callouts, heading anchors, copy controls, and figure labels.
- Agent launcher and panel controls.

Avoid:

- Generic AI marketing phrasing.
- Literal translation that changes product meaning.
- Long labels inside fixed-width buttons.

## Markdown Rendering Contract

Generated UI around Markdown must be bilingual:

- Heading anchor accessible labels.
- Code copy labels.
- Callout labels.
- Figure/caption fallback labels.
- Table overflow instructions if any.

Article body text remains author-authored content and should not be translated by UI logic.

## SEO Contract

SEO helpers should align with runtime language:

- `html[lang]`.
- Locale-aware date formatting where visible.
- Open Graph locale when generated by the client/server shell.
- Noindex behavior for owner routes independent of language.

If a route is owner-only or system-only, language support should not make it public-indexable.

## Mobile Fit Contract

Changed bilingual labels must be checked at:

- 390px mobile.
- 320px or equivalent narrow reflow pressure.
- Agent minimum desktop width.

Rules:

- Primary action labels should not wrap awkwardly on desktop.
- Mobile buttons can wrap only when the control remains visually deliberate.
- Chips and badges should truncate or wrap with `min-width: 0`.
- Long English technical words must not create horizontal page scroll.

## Implementation Slices

1. Inventory hard-coded public strings in changed surfaces.
2. Move Markdown-generated labels to i18n.
3. Add language runtime tests for storage fallback and route preservation.
4. Add public route screenshots in zh/en when labels change.
5. Add a lightweight i18n completeness check only if it can avoid false positives.

## Acceptance Checklist

- Changed public strings are available in Chinese and English.
- Language switching preserves route, query, and hash.
- `html[lang]` follows the selected language.
- Markdown renderer generated labels are not hard-coded English.
- No bilingual label causes horizontal overflow.
